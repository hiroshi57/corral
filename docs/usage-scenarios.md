# Corral はどんな時に使うのか（利用シナリオ）

> 「機能は分かったが、実際どう使うのか」に答えるための文書。
> **結論から言うと、Corral が効くのは「1人で順番にやると待ち時間が長い作業」を並べて回したい時です。**

---

## そもそも、今と何が変わるのか

### 今のやり方（Claude Code を1つ使う）

```
ターミナルを開く → 指示を出す → 終わるまで待つ（5〜20分）→ 結果を見る
→ 次の指示を出す → また待つ → …
```

- 待っている間、手が空く（別の作業に切り替えると集中が切れる）
- 複数の作業を同時に進めたい時は、ターミナルのタブを増やして自分で管理する
- どのタブが何をしていたか分からなくなる／終わったことに気づかない
- 変更をどう取り込んだか、後から追えない

### Corral を使うやり方

```
1画面で 5つの指示をまとめて出す → 全部が並列で走る
→ 終わったものが「要確認」に上がってくる（Chatwork にも通知）
→ 差分を見て承認 or 指摘して差し戻し
```

- **待ち時間が重なる**（5件×10分 = 50分 → 実質10〜15分）
- どれが動いていて、どれが終わったかが**一覧で分かる**
- 変更は**専用の作業コピー（git worktree）**で行われるので、自分が編集中のコードは汚れない
- 誰がいつ何を承認したか記録が残る（監査ログ）

---

## シナリオ1：提案書からタスクを起こして、まとめて片付ける

**こんな時**：クライアント提案の準備で、調査・資料作成・見積などやることが多い。

1. 提案書や議事録（Word / PDF / PowerPoint / Markdown）を **司令塔にドラッグ&ドロップ**
2. AI が内容を読んで**タスク候補に分解**（例：「競合の生成AI対策事例を調査」「提案骨子を作成」「見積根拠を整理」…）
3. 不要なものはチェックを外し、文言を直して **一括で起動**
4. 構成を選べる
   - **並列**：それぞれ独立して同時に進める（最速）
   - **段階（フェーズDAG）**：調査 → 骨子 → 見積 のように、前が終わってから次へ
5. 終わったものから順に差分を確認して承認

**効くポイント**：ドキュメントを起点にできるので、「まず何をタスクにするか」を人が書き出す手間が消える。

---

## シナリオ2：複数のダッシュボード／リポジトリを横断して同じ改修を入れる

**こんな時**：社内向けダッシュボードが十数本あり、全部に同じ改修（レスポンシブ対応、文言統一、ライブラリ更新など）を入れたい。

1. 案件（ワークスペース）に**対象リポジトリを複数登録**（マルチリポ）
2. 同じ指示を、リポジトリを変えて**台数指定で一括起動**
3. **📣 broadcast** で全ワーカーに追加指示（「余白は 16px で統一して」など）を一斉送信
4. 各リポの差分を1画面で確認 → 承認 → **PR を自動作成**（本文は実施内容・差分統計・コストから自動生成）

**効くポイント**：1本ずつ手作業で回すと半日かかる横断作業が、並列＋一括指示で圧縮できる。

---

## シナリオ3：定型の作業手順を「型」にして毎回使う

**こんな時**：バグ修正や新機能追加のたびに、毎回同じ順番（調査 → 原因特定 → 修正 → 回帰テスト）を踏んでいる。

1. **📚 プレイブック**から「バグ修正（再現→原因→修正→回帰テスト）」を選んで **▶ 展開**
2. 依存関係つきのタスクが自動で組まれ、順番に実行される
   - 「修正が失敗したら別アプローチを試す」という**失敗時の分岐**まで型に入れられる
3. 自分のやり方を型にしたい場合は、いまのタスク構成を**そのままテンプレとして保存**して次回から再利用

**効くポイント**：段取りを毎回考えなくてよくなる。チームで型を共有すれば、進め方が揃う。

---

## シナリオ4：夜間や離席中に走らせて、朝に確認する

**こんな時**：時間はかかるが判断が要らない作業（テスト追加、リファクタ、ドキュメント整備）を溜めている。

1. 作業をまとめて投入し、**自動承認（yolo）**をオンにする
2. **同時実行上限**を設定しておけば、マシンや API を使いすぎない
3. 完了・エラーは **Chatwork / Slack に通知**
4. 翌朝、**ダッシュボード**で「何件終わったか・いくらかかったか」を確認し、差分をまとめてレビュー

**効くポイント**：張り付いて待つ必要がなくなる。コストも見える。

## コードでない案件（提案書・議事録・レポート）の使い方

**Corral はプログラムのリポジトリ専用ではありません。** 資料フォルダをそのまま「案件」にできます。

### 設定

`corral.config.cmd` の `CORRAL_REPO` に、資料が入っているフォルダを指定するだけです。

```
set CORRAL_REPO=C:\Users\hiroshi_takizawa\Documents\LLMO提案_A社
```

- そのフォルダが変更履歴の管理下になければ、**初回に自動で用意します**（`git init` 相当）。
  これにより、資料の案件でも「作業コピーで安全に作業 → 差分を確認 → 承認して記録」が同じように使えます。
- 元のファイルは、承認するまで**一切変更されません**（エージェントは専用の作業コピーで作業します）。
- 日本語のファイル名もそのまま扱えます。
- 自動の履歴管理が不要なら `set CORRAL_AUTO_GIT_INIT=0` で無効化できます。

### 例：提案準備の案件

フォルダの中身:

```
LLMO提案_A社/
├─ 議事録.md            ← 打合せメモ
├─ 先方資料.pdf         ← もらった資料
└─ 参考_競合調査.xlsx
```

指示の例（そのまま貼って使えます）:

| やりたいこと | 指示 |
|---|---|
| 全体把握 | このフォルダの資料をすべて読み、何のための資料かを一覧にして `資料一覧.md` にまとめてください |
| 次の一手 | 議事録を読み、決定事項と課題から「次アクション一覧」を `次アクション.md` に（担当・期限欄つきで）作成してください |
| 提案骨子 | 資料をもとに提案の骨子（課題・打ち手・期待効果・進め方・概算費用）を `提案骨子.md` に作成してください |
| 想定質問 | 提案骨子に対して先方から出そうな質問と回答案を `想定QA.md` にまとめてください |

これを **並列**で一気に投げるか、**段階（フェーズDAG）**で「棚卸し → 骨子 → 想定QA」の順に流すのが効きます。
出来上がった `.md` はそのまま社内共有や資料化のベースに使えます。

> **注意**：PDF や Excel、Word の**中身の読み取りはエージェント側の能力に依存**します。
> 読めない形式は、テキストや Markdown に書き出してからフォルダに置くと確実です。
> （司令塔へのドラッグ&ドロップなら、PDF / Word / PowerPoint からタスクを抽出できます）

## 逆に、Corral を使わないほうがよい場面

正直に書きます。次のような時は普通に Claude Code を1つ使ったほうが速いです。

- **作業が1つだけ**（並列にする意味がない）
- **対話しながら詰めたい**（設計を相談しながら進める、探索的なデバッグ）
- **1〜2分で終わる小さな修正**（起動と承認の手間のほうが大きい）
- **1回きりの使い捨て作業**（案件として残す意味がない）

> **Corral の役目は「並べて回す・待たない・記録に残す」**です。
> 考えながら進める作業は、今まで通り1対1で対話するのが向いています。

## 共有された人が最初にやること（5分）

1. `start-corral.cmd` をダブルクリック → ブラウザが開く（緑の「本番」バッジを確認）
2. 画面左上の **「はじめに」** で案件の種類（**プログラム** / **資料・ドキュメント**）を選び、例をクリック
   - プログラムなら「コードを調べてもらう」／資料なら「資料を棚卸ししてもらう」
   - どちらも**新規ファイルを1つ作るだけ**なので安全です
3. ワーカーが「実行中 → 要確認」に変わったらクリックして **「差分」タブ**で中身を見る
4. 問題なければ **✓ 承認して commit**、直したい行はクリックして指摘 → 差し戻し

ここまで通せば、Corral の一周（指示 → 並列実行 → 確認 → 承認）が体感できます。
そのうえで、シナリオ1〜4のどれが自分の仕事に当てはまるか考えるのが早いです。
